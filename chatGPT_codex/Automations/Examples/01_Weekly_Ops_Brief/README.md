# 排程範例 01：每週營運簡報

> 🔵 **方案需求**：Plus 起。

**類型**：獨立任務（每次執行開新 chat）
**頻率**：每週一 09:00（Asia/Taipei）
**授權**：唯讀 + 寫入指定目錄

---

## 為什麼用「獨立任務」

週報每次都應該**從零開始**，不需要上週的對話上下文。掛在現有 chat 反而會累積無關的歷史。

> 對照：[範例 02 庫存監控](../02_Inventory_Monitor/README.md)用的是「掛在現有 chat」，因為它需要記得上次通知過什麼。

---

## 📋 建立前的必要步驟

本章可完全離線練習：[`student-lab/tideflow-portal`](../../../student-lab/tideflow-portal/README.md)已附配送、Issue、PR、commit 偽資料與週報產生器。先在副本執行 `npm run report`；有 Automation 權限時，再把相同規則設成排程。

> [!IMPORTANT]
> **先在一般 chat 手動跑一次。** 排程出錯時你不在現場。

手動測試用的 prompt 與下方排程完全相同。確認：
- [ ] 產出的格式可用
- [ ] 數字正確
- [ ] 缺漏資料被正確處理
- [ ] 沒有寫入非預期的路徑

---

## ⚙️ 排程設定

```text
每週一上午 9:00（Asia/Taipei），彙整 tideflow-portal 上週的變更與營運數據。

## 資料來源
- git log（上週的 commit）
- `data/` 目錄下上週的配送 CSV
- 開放中的 PR 與 Issue

## 產出
寫入 `reports/YYYY-WW_週報.md`
- **只能新增檔案，不可覆寫已存在的週報。**
- 檔案已存在時，改寫入 `reports/YYYY-WW_週報_v2.md` 並在通知中說明。

## 內容結構
1. 已完成（依 commit 分類，附 PR 連結）
2. 風險（測試失敗、超過 7 天未更新的 PR、未處理的 TODO）
3. 本週建議優先處理事項（最多 3 項，附理由）
4. 營運數據摘要（各區單量、準時率）

## 限制
- 不要修改 `data/` 或 `src/` 底下任何檔案。
- 不要提交或推送任何變更。
- 不要寄送郵件、不要在 GitHub 留言。
- **資料缺漏時標示「資料缺漏」，不可用 0 或推估值填補。**

## 通知
- 產出成功且無風險項目 → **不要通知我。**
- 出現下列任一情況才通知：
  - 有測試失敗的 PR
  - 有超過 7 天未更新的開放 PR
  - 準時率低於 95%
  - 資料缺漏超過 3 天
```

---

## 🔕 為什麼要寫「不通知」

> [!WARNING]
> **每次都通知的排程，兩週後就會被忽略。** 這比沒有排程更糟——你以為有人在看，其實沒有。

沒有通知條件的版本：

```text
❌ 每週一整理上週變更並回報。
```

52 週後你會收到 52 則通知，其中約 45 則是「一切正常」。第 46 則真的有問題時，你已經養成滑過去的習慣了。

執行結果仍會出現在 **Scheduled 收件匣**，有發現的執行會標為未讀——你隨時可以主動去看。

---

## 🔧 RRULE 版本

若需要更精確的排程：

```text
RRULE:FREQ=WEEKLY;BYDAY=MO;BYHOUR=9;BYMINUTE=0
```

其他常用：

| 需求 | RRULE |
| :--- | :--- |
| 每週一到週五 08:30 | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=8;BYMINUTE=30` |
| 每月 1 號 09:00 | `FREQ=MONTHLY;BYMONTHDAY=1;BYHOUR=9;BYMINUTE=0` |
| 每季首日 | `FREQ=MONTHLY;INTERVAL=3;BYMONTHDAY=1` |
