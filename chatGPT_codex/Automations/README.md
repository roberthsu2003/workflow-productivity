# Automations（排程任務）

> 🔵 **方案需求**：Plus 起。**事件觸發**（Gmail / Slack / GitHub）僅在 ChatGPT **網頁版與行動版**可用，桌面版與 CLI 不支援。Business / Enterprise 由管理員以 **Allow event-triggered scheduled tasks** 權限控管。

把重複性工作交給 Codex 定時執行：週報彙整、庫存監控、競品追蹤、CI 健康度檢查。即使你的電腦休眠，雲端排程仍會準時執行。

---

## ⏰ 兩種觸發方式

| 類型 | 怎麼觸發 | 適合 |
| :--- | :--- | :--- |
| **時間排程** | 固定週期（分鐘 / 每日 / 每週 / RRULE） | 週報、日報、批次處理、監控輪詢 |
| **事件觸發** | Gmail、Slack、GitHub 的事件 | 收到特定郵件、PR 開啟、Slack 提及 |

### 兩種掛載方式

| 方式 | 行為 | 適合 |
| :--- | :--- | :--- |
| **獨立任務** | 每次執行開一個新 chat | 每次都應從零開始的週報、批次流程 |
| **掛在現有 chat** | 保留該 chat 的上下文，週期醒來檢查狀態 | 監控、追蹤某件事的進展 |

> **對照 Claude**：這兩種方式類似 heartbeat（附著於目前工作，週期醒來）與 cron（獨立工作，固定時間執行）的分別。

## 🛠️ 建立方式

### 用對話建立

直接描述**工作內容、時間與產出去向**：

```text
每週一上午 9:00（Asia/Taipei）檢查 tideflow-portal 過去一週的變更，
整理成三段：已完成事項、風險、本週待辦。

條件：
- 沒有新變更時**不要通知我**。
- 若測試失敗或需要人工決策，在這個 chat 提醒我。
- 只讀取 repo，不要修改任何檔案。
```

### 精確排程：RFC 5545 RRULE

進階排程可直接編輯 recurrence rule：

```text
RRULE:FREQ=MONTHLY;BYMONTHDAY=1;BYHOUR=9;BYMINUTE=0
```

| 需求 | RRULE |
| :--- | :--- |
| 每月 1 號早上 9 點 | `FREQ=MONTHLY;BYMONTHDAY=1;BYHOUR=9;BYMINUTE=0` |
| 每週一到週五早上 8:30 | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=8;BYMINUTE=30` |
| 每季第一天 | `FREQ=MONTHLY;INTERVAL=3;BYMONTHDAY=1` |
| 每天每 4 小時 | `FREQ=HOURLY;INTERVAL=4` |

## ✅ 建立前的必要步驟

> [!IMPORTANT]
> ### 排程之前，一定要先手動跑通一次
> 官方明確建議：*"Before you schedule a task, test the prompt manually in a regular chat first."*
>
> 理由很實際——**排程任務出錯時你不在現場。** 手動跑一次可以確認：
> - 指示是否清楚無歧義
> - 工具行為是否符合預期
> - 輸出品質是否可用
> - 需要的權限是否已就緒

### 建立時必須指定的六件事

- [ ] **資料來源**：讀哪些檔案、哪個 repo、哪個資料夾
- [ ] **時區**：`Asia/Taipei`。不寫的話跨時區會出事
- [ ] **頻率**：每天？每週？每小時？
- [ ] **完成條件**：怎樣算這次執行成功
- [ ] **通知條件**：**什麼情況才通知我**（見下方）
- [ ] **授權範圍**：只讀？可寫入？可寄信？

## 🔕 通知疲勞：排程任務的頭號殺手

> [!WARNING]
> **每次都通知的排程任務，兩週後就會被忽略。** 這比沒有排程更糟——你以為有人在看，其實沒有。

### 一律加入「無事不擾」條款

```text
❌ 每天早上整理昨天的錯誤日誌並回報。

✅ 每天早上 8:00（Asia/Taipei）檢查昨天的錯誤日誌。
   - **錯誤數量在正常範圍（< 50 筆）時不要通知。**
   - 出現新型態的錯誤，或總數超過 50 筆時才通知。
   - 通知時附上：錯誤類型、發生次數、最早出現時間、相關檔案。
```

執行結果會出現在 **Scheduled 收件匣**，有發現的執行會標記為未讀。

## 🔐 寫入型任務的授權邊界

> [!WARNING]
> **排程任務執行時你不在旁邊，沒有人可以按「取消」。**
>
> 涉及寫入、寄信、發佈或刪除資料的排程，必須有明確的授權與審核邊界。

### 建議的分級

| 動作 | 排程可以做嗎 |
| :--- | :---: |
| 讀取檔案、分析、產出報告 | ✅ |
| 寫入到指定的 `reports/` 目錄 | ✅ 範圍明確即可 |
| 建立 Gmail **草稿** | ✅ |
| **寄出**郵件 | ⚠️ 需極明確的收件人與內容範本 |
| 修改程式碼、提交、推送 | ⚠️ 限定分支，且不可推 main |
| 刪除任何東西 | ❌ **不要讓排程做刪除** |
| 對外發佈（Sites、社群） | ❌ 產草稿就好 |

### 範本：安全的寫入型排程

```text
每週五下午 5:00（Asia/Taipei）產出潮汐物流的週報。

資料來源：
- `data/` 目錄下本週的配送 CSV
- git log（本週的程式碼變更）

產出：
- 寫入 `reports/YYYY-WW_週報.md`
- **只能新增檔案，不可覆寫已存在的週報。**

限制：
- 不要修改 `data/` 底下任何檔案。
- 不要提交或推送任何變更。
- 不要寄送郵件。

通知：
- 產出成功且無異常 → 不通知。
- 準時率低於 95%、或資料缺漏超過 3 天 → 通知我並附說明。
```

## 🧪 三個課堂範例

### 範例一：週報彙整（獨立任務）

```text
每週一上午 9:00（Asia/Taipei），彙整 tideflow-portal 上週的變更。

輸出三段：
1. 已完成（依 commit 分類，附 PR 連結）
2. 風險（測試失敗、未處理的 TODO、超過 7 天未更新的 PR）
3. 本週建議優先處理事項（最多 3 項，附理由）

限制：只讀，不修改任何檔案。
通知：無變更時不通知。
```

### 範例二：庫存監控（掛在現有 chat）

```text
在這個 chat 中，每天上午 10:00 與下午 4:00（Asia/Taipei）
檢查 `data/inventory.csv`。

通知條件（只在符合時才通知）：
- 任何品項庫存低於安全水位
- 任何品項 3 天內庫存歸零的預測

通知內容：品項、目前庫存、安全水位、預估耗盡日期。
限制：只讀，不修改 CSV。
```

### 範例三：CI 健康度（事件觸發）

```text
當 tideflow-portal 有新的 PR 開啟時：
1. 檢查是否符合 AGENTS.md 的 code review rules
2. 標記出未處理的 Promise rejection 與字串拼接的 SQL
3. 確認是否有對應的回歸測試

限制：
- **只留下審查意見，不要修改程式碼、不要 approve、不要 merge。**
- 沒有發現問題時不要留言。
```

> 事件觸發需在 ChatGPT 網頁版或行動版建立；企業環境需管理員開啟 **Allow event-triggered scheduled tasks**。

## 🔄 與 Claude Scheduled 的對照

| 面向 | Claude Scheduled | Codex Automations |
| :--- | :--- | :--- |
| 方案 | Pro / Max / Team / Enterprise | 🔵 Plus 起 |
| 觸發方式 | 時間排程 | **時間排程 + 事件觸發**（Gmail / Slack / GitHub） |
| 精確排程 | 介面設定 | **RFC 5545 RRULE** |
| 掛載方式 | 獨立任務 | 獨立任務 **或** 掛在現有 chat |
| 可用介面 | Cowork | 事件觸發僅限**網頁版與行動版** |
| 能改檔嗎 | 否 | **可以**（所以授權邊界更重要） |

## ✅ 上線前檢查清單

- [ ] 已在一般 chat 手動跑通至少一次
- [ ] 時區明確寫出（`Asia/Taipei`）
- [ ] **有寫「什麼情況不通知」**
- [ ] 授權範圍明確，沒有刪除與對外發佈權限
- [ ] 產出路徑明確，且不會覆寫既有檔案
- [ ] 失敗時的行為已定義（重試？通知？靜默？）
- [ ] 已在行事曆上標記「一個月後檢視這個排程還需不需要」
