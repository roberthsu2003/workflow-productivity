# 03-3. Release Note 產生

> 🔵 **方案需求**：Plus 起（連接 GitHub）。純資料改寫部分 🟢 Free 可練。

**情境**：`tideflow-portal` 要發 `v2.8.0`。兩週累積了 22 個 commit，你要寫一份**使用者看得懂**的版本說明。

> **這一章練的是「翻譯」**：把工程語言翻成使用者語言，並在過程中決定什麼該講、什麼不該講。

---

## 📂 示範資料

[`tideflow_commit_log.md`](./sample_files/tideflow_commit_log.md) — 22 個 commit，含：

- 9 個使用者可感知的變更
- 13 個使用者感受不到的變更
- **2 個需要特別處理的項目**（安全性修正、執行環境變更）

---

## 🥇 練習一：分類與取捨

```markdown
## Goal
把 v2.7.0 → v2.8.0 的 22 個 commit 分類，決定哪些該寫進對外的 release note。

## Context
- 資料來源：`tideflow_commit_log.md`
- Release note 的讀者：**使用 tideflow-portal 的電商客戶**（非工程人員）

## Scope
- **只做分類與取捨，這一輪不要寫文案。**
- 不要修改 commit log。

## Verification
輸出一張表：
| Commit | 類型 | 使用者感受得到嗎 | 該寫進 release note 嗎 | 理由 |

最後另列：
1. **需要特別處理的項目**——有沒有哪些變更不能直白地寫出來？為什麼？
2. 有沒有哪些變更**只跟部分讀者有關**？
```

### 📝 解答對照（講師用）

應該抓到兩個特殊項目：

| Commit | 特殊之處 | 正確處理 |
| :--- | :--- | :--- |
| `8a15e3f` session token 未正確續期 | **安全性修正** | 不詳述漏洞細節（避免提供攻擊線索），但要提示使用者重新登入 |
| `2e8f9a5` 升級 Node.js 22.8.0 | **執行環境變更** | 只跟**自架部署**的客戶有關，SaaS 使用者不需要。需分段處理 |

> **教學重點**：Release note 不是 commit log 的翻譯，而是**編輯決策**。
>
> - 安全性修正：透明 vs. 不提供攻擊線索之間要拿捏
> - 環境變更：不同讀者需要的資訊不同
>
> 直接把 22 個 commit 全部列出來的 release note，等於沒寫。

## 🥈 練習二：撰寫 release note

```markdown
## Goal
撰寫 v2.8.0 的對外 release note。

## Context
- 讀者：使用 tideflow-portal 的電商客戶，非工程背景
- 分類結果依練習一
- 發布日期：2026-09-08

## Scope
- **用使用者的語言，不要用 commit message 的語言。**
  ❌「修正 PICKUP enum 未處理」
  ✅「選擇門市自取時，結帳金額不再多計運費」
- 安全性修正**不詳述漏洞細節**，但要說明使用者該做什麼。
- 自架部署相關的變更另列一段。
- 寫入 `CHANGELOG.md`，**在最上方新增章節，不要覆蓋既有內容**。

## Verification
結構：
1. **新功能**（使用者最想看的放最前面）
2. **問題修正**
3. **效能改善**（有具體數字就寫數字）
4. **給自架部署客戶的注意事項**
5. **建議動作**（如：建議重新登入）

每一項都用「使用者會遇到什麼情況 → 現在如何」的句型。
```

### 參考方向

> ## v2.8.0 — 2026-09-08
>
> ### ✨ 新功能
>
> - **超商取貨**：結帳時可選擇 7-11 或全家門市取貨。
> - **配送績效匯出**：後台新增報表匯出功能，可下載各區配送數據。
>
> ### 🐛 問題修正
>
> - 選擇「門市自取」時，結帳金額不再誤計運費。
> - 訂單通知信中的訂單編號正常顯示（先前部分信件顯示為 undefined）。
> - 後台匯出的 CSV 用 Excel 開啟時不再出現中文亂碼。
> - 手動輸入的收件地址不會被自動補完功能覆蓋。
> - 修正部分使用者登入後偶爾被登出的問題。**建議您重新登入一次。**
> - 修正 Safari 瀏覽器上結帳頁面的版面問題。
>
> ### ⚡ 效能改善
>
> - 配送查詢速度大幅提升：P95 回應時間從 3.2 秒縮短至 0.48 秒。
>
> ### 🔧 自架部署客戶請注意
>
> - 本版本執行環境升級至 **Node.js 22.8.0 LTS**。升級前請確認您的部署環境已支援。
> - 本版本包含一個資料庫 migration（`20260904_add_shipment_region_idx`），部署時會自動套用。

**注意**：
- 「修正部分使用者登入後偶爾被登出」——沒說是 session token 續期漏洞，但給了行動建議
- 效能改善**有具體數字**，比「速度提升」有說服力
- 自架部署的注意事項單獨一段

## 🥉 練習三：內部版 vs. 對外版

同一批 commit，給工程團隊看的版本完全不同。

```markdown
## Goal
額外產出一份**內部版**的 v2.8.0 變更說明，供工程團隊參考。

## Scope
- 寫入 `docs/internal/v2.8.0_internal_notes.md`
- 不要修改對外的 `CHANGELOG.md`

## Verification
內部版需包含對外版**刻意省略**的資訊：
1. 技術細節（session token 續期的具體問題、索引加在哪個欄位）
2. 重構與技術債清償（移除 moment.js，包體積 -182KB）
3. 測試覆蓋的變化
4. **需要後續追蹤的事項**
5. 依賴升級清單

最後對照：對外版與內部版的差異在哪？為什麼要這樣區分？
```

> **教學重點**：這個練習讓學員意識到**同一份資料，不同讀者需要不同的產出**。這是 release note 的本質，也是很多技術寫作的本質。

## 🏁 練習四：做成 Skill

發版是每個 sprint 都會做的事。

```markdown
## Goal
把 release note 產生流程做成 skill。

## Scope
- 建立 `.agents/skills/release-notes/SKILL.md`

## Verification
SKILL.md 需包含：
1. `description`：何時觸發（發版時）、何時不觸發（一般 commit）
2. 步驟：取 commit 範圍 → 分類 → 判斷讀者可感知性 → **識別敏感項目** → 改寫 → 寫入 CHANGELOG
3. **敏感項目的處理原則**（安全性修正不詳述細節、環境變更分段）
4. 輸出格式（五段結構）
5. 限制：不可覆蓋既有 CHANGELOG 內容、不可自行發布 release
```

> 詳見 [Skills 章節](../../../Skills/README.md)。
