# 03-1. Issue 分流

> 🔵 **方案需求**：Plus 起。純資料分析部分（不連 GitHub，直接讀 CSV）🟢 Free 可練。

**情境**：`tideflow-portal` 的 Issue 累積了 12 個未處理項目。下週的 sprint 只能排 4 個。你要決定哪 4 個。

> **這個練習不需要讀程式碼**，適合非工程背景的學員。它練的是**優先度判準**。

---

## 📂 示範資料

[`tideflow_issue_backlog.csv`](./sample_files/tideflow_issue_backlog.csv) — 12 個 Issue，欄位：編號、標題、類型、狀態、建立日期、留言數、現有優先度、備註。

---

## 🥇 練習一：先看資料，別急著排序

```markdown
## Goal
盤點這 12 個 Issue 的分布，說明現有的優先度標記是否可信。

## Context
- 資料來源：`tideflow_issue_backlog.csv`
- 「現有優先度」欄位是由不同工程師各自標的，沒有統一標準。

## Scope
- **只做盤點，這一輪不要排序、不要建議。**
- 不要修改 CSV，不要在 GitHub 上異動任何 Issue。

## Verification
輸出：
1. 依類型分布（bug / feature / performance / docs / tech-debt / chore）
2. 依現有優先度分布（P1 / P2 / P3）
3. **留言數與現有優先度的關係**——高留言數的都是高優先度嗎？
4. 你認為現有優先度標記有哪些可疑之處？
```

### 📝 觀察重點（講師用）

資料中刻意設計了兩組矛盾：

| Issue | 留言數 | 現有優先度 | 矛盾 |
| :---: | :---: | :---: | :--- |
| #421 希望支援超商取貨 | **41**（最高） | P2 | 討論最熱烈，但只是 feature request |
| #435 新增深色模式 | 33 | P3 | 留言多，但優先度最低 |
| #436 訂單編號顯示 undefined | 15 | P1 | 留言不多，但影響每一封通知信 |
| #438 升級 Node.js 22 | **1**（最低） | P3 | 沒人討論，但可能是安全性問題 |

> **教學重點**：**留言數反映的是「討論熱度」，不是「業務影響」。** 深色模式很多人想要，但它壞掉不會讓公司損失營收；訂單編號顯示 undefined 沒什麼人留言，但每個下單的客戶都看得到。

---

## 🥈 練習二：建立判準，再排序

```markdown
## Goal
為下週 sprint 選出 4 個 Issue，並說明為什麼是這 4 個。

## Context
- 團隊下週可用工時：約 4 人天
- 業務背景：秋季新品 10/5 上市，屆時流量會上升
- 現有優先度標記不可信（見練習一）

## Scope
- **不要修改 GitHub 上的任何 Issue**（不改標籤、不關閉、不指派）。
- 只提建議。

## Verification
1. 先寫出你的**優先度判準**（在排序之前，不是之後）
   建議維度：業務影響 / 使用者觸及範圍 / 修復成本 / 時效性 / 風險
2. 用這套判準對 12 個 Issue 逐一評分
3. 選出 4 個並排序
4. **明確說出你捨棄了什麼，以及捨棄的代價**
5. 列出你缺少、但會影響判斷的資訊
```

> **第 1 點的順序很重要。** 先排序再補理由，是合理化；先立判準再排序，才是判斷。這個要求會逼出比較誠實的推理。

### 參考答案的方向（無標準答案）

合理的前 4 名可能是：

| 順序 | Issue | 理由 |
| :---: | :--- | :--- |
| 1 | #412 門市自取仍計運費 | 直接影響營收、有客訴、10/5 前必須修 |
| 2 | #423 配送查詢 API 超過 3 秒 | 新品上市流量會上升，尖峰會惡化 |
| 3 | #436 訂單編號 undefined | 每封通知信都受影響，觸及範圍最廣 |
| 4 | #433 CSV 中文亂碼 | 修復成本極低（加 BOM），CP 值高 |

**捨棄的代價**：#421 超商取貨討論最熱烈，延後會讓提出者失望——建議在 Issue 中回覆說明排程理由，而不是靜默擱置。

## 🥉 練習三：產出 sprint 規劃

```markdown
## Goal
把分流結果整理成下週 sprint 的規劃文件。

## Scope
- 寫入 `docs/sprint/2026-W38_sprint_plan.md`。
- **不要在 GitHub 上異動任何 Issue。**

## Verification
文件包含：
1. 本週選入的 4 個 Issue（含編號、標題、預估工時、負責人欄位留空）
2. 判準與評分表
3. **未選入項目的處理建議**——哪些要在 Issue 中回覆說明？哪些可以直接關閉？
4. 風險提醒（如：#431「登入後偶爾跳回首頁」無法穩定重現，可能耗時超出預估）
```

> **第 3 點常被忽略。** 未選入的 Issue 也需要處理——至少要讓回報者知道你看到了。

## 🏁 練習四（進階）：連接真實 GitHub

前三個練習都是讀 CSV。這個練習連上真正的 GitHub。

```markdown
## Goal
分析我的測試 repo `<你的帳號>/<測試repo>` 中的開放 Issue，做同樣的分流。

## Scope
- **只讀取。不要建立、修改、關閉或指派任何 Issue。**
- 不要留言。
- 不要修改標籤。

## Verification
- 輸出同練習二的格式
- **最後列出你實際呼叫了哪些 GitHub 操作**，讓我確認全部都是讀取
```

> **最後那一句是好習慣**：要求代理回報自己做了什麼，比事後檢查快得多。
