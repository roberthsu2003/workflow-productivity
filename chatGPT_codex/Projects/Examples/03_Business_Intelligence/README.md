# 範例 03：商業情報

> 🟢 **方案需求**：Free（Local project 讀取本機 CSV、產出報表，Free 可完成）

**情境**：季度結束，你要做上半年配送績效分析。資料分散在兩個檔案（Q1、Q2），而且**其中有一個月的資料是缺的**。

> **這個範例練的是 Local project**——Codex 直接讀你電腦上的檔案，不需要上傳。

---

## 📂 檔案

| 檔案 | 說明 |
| :--- | :--- |
| [`sample_files/配送績效_2026Q1.csv`](./sample_files/配送績效_2026Q1.csv) | 1–3 月，4 區 ×3 月 = 12 列 |
| [`sample_files/配送績效_2026Q2.csv`](./sample_files/配送績效_2026Q2.csv) | 4–6 月，**含一列缺漏** |
| [`sample_files/區域代碼對照表.csv`](./sample_files/區域代碼對照表.csv) | 區域代碼、涵蓋縣市、標準工作天 |

**欄位**：月份、區域代碼、區域名稱、配送單量、準時率(%)、平均配送時數、異常件數、客訴件數、備註

## 🏗️ 課前設定

與前兩個範例不同，**這裡用 Local project**：

1. 把 `sample_files/` 複製到你的練習資料夾，例如 `~/codex-lab/tideflow-bi/`
2. `git init && git add . && git commit -m "init"`（**重要**：Codex 會產生檔案）
3. 在 Codex 中建立 Local project，綁定該資料夾

```bash
mkdir -p ~/codex-lab/tideflow-bi/data
cp sample_files/*.csv ~/codex-lab/tideflow-bi/data/
cd ~/codex-lab/tideflow-bi
git init && git add . && git commit -m "init: 配送績效原始資料"
```

> ### Local project 與 ChatGPT project 的差別

## 🥇 練習一：資料品質盤點（不可跳過）

```markdown
## Goal
盤點 data/ 目錄下的三個 CSV，說明資料品質。

## Scope
- **只讀取，不要修改任何檔案，也不要產生新檔案。**
- 這一輪不要做分析。

## Verification
輸出：
1. 每個檔案的列數、欄位、涵蓋範圍
2. **資料品質問題清單**（缺漏、格式不一致、可疑值）
3. 三個檔案之間的關聯（哪個欄位可以 join？）
4. 這批資料**無法**回答的問題
```

**預期它應該發現**：`配送績效_2026Q2.csv` 中，`2026-06,Central` 這列的所有數值欄位皆為空，備註寫「WMS 系統移轉期間未落帳」。

> 如果它沒發現，這就是最好的教材——**證明「先盤點」不是多餘的步驟**。直接叫它做分析，你會拿到一份把空值當 0 算的報告。

## 🥈 練習二：上半年分析（缺漏值是重點）

```markdown
## Goal
產出 2026 上半年配送績效分析，供管理層檢視。

## Context
- 資料：`data/配送績效_2026Q1.csv` + `data/配送績效_2026Q2.csv`
- 區域對照：`data/區域代碼對照表.csv`
- 公司準時率目標：95.0%
- 東區另有獨立目標：92.0%

## Scope
- **不要修改原始 CSV。**
- **中區 2026-06 資料缺漏。計算任何平均值時必須排除該筆並註明，
  絕對不可用 0 代替，也不可用鄰月推估。**
- 分析結果寫入 `reports/2026H1_配送績效分析.md`。

## Verification
1. 各區上半年彙總（單量、平均準時率、平均配送時數）
2. 對照目標的達成情況
3. **每一個平均值都要註明「計算基礎是幾個月」**
   （中區只有 5 個月，其他區 6 個月）
4. 你做過的所有假設
5. 資料缺漏對結論可信度的影響
```

### 📝 驗收重點（講師用）

| 檢查 | 正確 | 錯誤 |
| :--- | :--- | :--- |
| 中區平均準時率 | 用 **5 個月**計算並註明 | 用 6 個月（把空值當 0）→ 數字會低到荒謬 |
| 中區單量彙總 | 標「5 個月合計，6 月資料缺漏」 | 直接加總說是「上半年合計」 |
| 區域比較 | 註明中區的基礎不同，不宜直接比較 | 直接排名 |

> [!WARNING]
> **把空值當 0 是這個練習最重要的失敗模式。**
>
> 如果模型算出「中區上半年平均準時率 80.7%」，那就是把 6 月的空值當成 0% 了。正確答案應該在 96–97% 之間（5 個月的平均）。
>
> 這個錯誤在真實工作中會導致嚴重誤判——你會以為中區出了大事，實際上只是資料沒落帳。

## 🥉 練習三：跨檔 join 與衍生指標

```markdown
## Goal
結合區域對照表，計算「相對於標準工作天的表現」。

## Context
- 各區的標準工作天不同（北區 1 天、中南區 2 天、東區 3 天）
- 平均配送時數以小時計

## Scope
- 不要修改原始 CSV。
- 新增欄位的計算邏輯要寫清楚。

## Verification
1. 各區的「實際配送時數 ÷ (標準工作天 × 24)」比值
2. 這個指標說明了什麼？東區的絕對時數最長，但**相對於標準**呢？
3. 這個指標有什麼**侷限**？（例如：標準工作天本身是怎麼訂的？合理嗎？）
```

> **第 3 點是關鍵。** 好的分析師會質疑指標本身。東區標準 3 天 = 72 小時，實際 38 小時，看起來「超前」——但這是不是因為標準訂得太寬鬆？

## 🏁 練習四：產出試算表

```markdown
## Goal
產出管理層會議用的試算表。

## Scope
- **不要修改原始 CSV。**
- 輸出 `reports/2026H1_配送績效.xlsx`

## Verification
三個工作表：
1. **明細**：兩季合併，首列凍結，缺漏列以明顯標示（不可留白也不可填 0）
2. **彙總**：各區彙總，含「計算基礎月數」欄位
3. **對照目標**：目標 / 實際 / 差距 / 判定

完成後在對話中列出：你在試算表中如何呈現缺漏資料？
```

## 🔍 練習五（進階）：把分析做成可重複執行的腳本

```markdown
## Goal
把分析邏輯寫成腳本，下一季可直接重跑。

## Scope
- `scripts/analyze_delivery.py`
- 接受 CSV 路徑作為參數，不要硬編碼檔名
- **缺漏值處理邏輯必須明確寫在程式碼中並加註解**

## Verification
- 對 Q1+Q2 執行，結果與練習二一致
- 腳本應在遇到缺漏值時**印出警告**，而不是靜默略過
- 加一個測試：故意餵含缺漏的資料，確認它有正確排除
```

> **這是 Local project 的核心價值**：分析不再是一次性的對話，而是**可重複執行、可版控、可測試的程式碼**。
