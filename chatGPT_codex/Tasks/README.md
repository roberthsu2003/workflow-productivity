# Tasks（任務與提示詞）

> 🟢 **方案需求**：Free（完全可用）。檔案產出、圖片生成與 Visualizations 依方案而異，見各範例標註。

在 Codex，每一段工作是一個 **task**。這是本講義最核心的一章——**寫得好的 task，決定了 Codex 是幫手還是麻煩。**

---

## ⚠️ Task 的上下文與範圍限制

> [!WARNING]
> ### 📌 一個 task = 一個可驗收的目標
> - **不相干的目標必須拆成不同 task。** 「順便幫我把測試也修一下」是最常見的失控起點。
> - **同一個 repo 不要讓兩個 task 同時改同一批檔案。** 需要平行處理時，請用 Git worktree（見 [Workspaces](../Workspaces/README.md)）。

> [!IMPORTANT]
> ### 💡 上下文消耗機制
> - **每一輪都會重讀**：同一個 task 中，每次新提問時，先前的對話、讀過的檔案內容都會重新進入 context window。
> - **Codex 會主動讀檔**：與 Claude 不同，你不需要上傳整份程式碼——**指出檔案路徑就好**。它會自己去讀，而且只讀需要的部分。貼整份程式碼進 prompt 反而會浪費上下文。
> - **長對話會變鈍**：階段性任務完成後，開新 task。跨 task 需要共用的規則，寫進 `AGENTS.md`；跨 task 需要共用的流程，做成 Skill。

### 🛠️ 最佳實務
1. **指路，不要餵食**：寫「`src/api/orders.ts` 的第 40 行附近」，而不是貼 300 行程式碼。
2. **長期規範改用 [`AGENTS.md`](../Agent_Configuration/README.md)**：每次都要交代的事（用什麼套件管理器、測試怎麼跑），寫一次就好。
3. **重複流程改做 [Skill](../Skills/README.md)**：每週都要做的報表流程，不要每次重寫 prompt。

## 📐 GCSV 框架（Codex 版的 RTCCF）

Claude 用 **RTCCF**（Role／Task／Context／Constraint／Format），因為它產出的是「內容」，需要指定角色與版面。

Codex 產出的是「已驗證的變更」，所以框架換成 **GCSV**：

| 代號 | 英文 | 建議寫什麼 |
|------|------|------------|
| **G** | **Goal** | 要達成的**可觀察結果**（不是「幫我看一下」，而是「讓 `npm test` 全綠」） |
| **C** | **Context** | 業務目的、使用者、相關**檔案路徑**、既有行為、重現步驟 |
| **S** | **Scope** | **可以動什麼、不可以動什麼**。技術與格式限制 |
| **V** | **Verification** | 怎樣算做完？跑哪個測試？看哪個畫面？ |

> **與 RTCCF 的對照**：`Role` 在 Codex 通常不必寫（它本來就是工程代理，角色寫進 `AGENTS.md` 更有效）；`Format` 被 `Verification` 取代——重點不是版面長怎樣，而是**怎麼證明它做對了**。

### 可複製的空白範本

```markdown
## Goal
（要完成的可觀察結果）

## Context
- 業務目的：
- 相關檔案：`path/to/file.ts`、`path/to/other.ts`
- 現況／重現步驟：
  1.
  2.

## Scope
- 可修改：
- 不可修改：
- 限制：

## Verification
- （必須通過的測試或可觀察結果）
```

## 🗂️ 五種任務型態

不同型態的 task，授權範圍完全不同。**先判斷型態，再選範本。**

| 型態 | 授權 | 典型開場白 |
| :--- | :--- | :--- |
| 一、問答／檢視 | 只讀 | 「請閱讀…並整理…，不要修改任何檔案」 |
| 二、診斷 | 只讀 + 可執行 | 「請找出原因與證據；先不要修復」 |
| 三、建構／修改 | 可改指定範圍 | 「請修改 X，範圍限於…」 |
| 四、產出文件與資料 | 可寫新檔 | 「請產生…，不要更動原始資料」 |
| 五、長時工作 | 依授權，分階段 | `/goal` + 明確完成條件 |

## 範例一：問答／檢視（只讀）

### 任務背景

你接手 **潮汐物流（TideFlow Logistics）** 的 `tideflow-portal` 專案，需要在動手前先建立全貌認知，並確認 Codex 對這個 repo 的理解沒有幻覺。

### GCSV Prompt（請複製後修改）

```markdown
## Goal
產出一份 `tideflow-portal` 的技術現況摘要，讓新進工程師 30 分鐘內能上手。

## Context
- 我剛接手這個 repo，沒有前手交接文件。
- 入口大致在 `src/` 與 `package.json`，但我不確定完整結構。

## Scope
- **不要修改任何檔案，也不要執行安裝或建置命令。**
- 只讀取 repo 內的檔案，不要上網查詢。

## Verification
輸出需包含四段：
1. 專案用途（一段話）
2. 技術棧與版本（附你是從哪個檔案讀到的）
3. 目錄結構與各層職責
4. **你無法從 repo 確認的項目清單**——這一段不可以空白，也不可以用猜測填滿
```

> **課堂重點**：第 4 點是這個 prompt 的靈魂。它把「誠實」變成可驗收項目。如果 Codex 硬要把不確定的事寫得很篤定，代表你的 repo 缺可讀說明。

## 範例二：診斷（只讀 + 可執行）

### 任務背景

麥禾烘焙的線上訂購頁面，客訴反映「選了門市自取，結帳時運費還是被算進去」。你要先確認原因，**還不打算讓 Codex 動手修**。

### GCSV Prompt（請複製後修改）

```markdown
## Goal
找出「門市自取仍計算運費」的根本原因，並提出修復方案供我選擇。

## Context
- 重現步驟：
  1. 前往 `/checkout`
  2. 配送方式選「門市自取」
  3. 觀察小計區塊 → 運費 NT$80 仍存在
- 相關檔案（我推測，未必正確）：`src/checkout/` 底下
- 這個 bug 大約在上週的改版後出現。

## Scope
- **只做診斷，不要修復。**
- 可以執行測試與讀取 git log／git blame。
- 不要修改任何檔案。

## Verification
輸出需包含：
1. 根本原因（指出**確切的檔案與行號**）
2. 支持這個判斷的證據（程式碼片段或 git 紀錄）
3. 2～3 個修復方案，各自的影響範圍與風險
4. 建議補哪一個回歸測試
```

> [!IMPORTANT]
> **「先診斷、後修復」是使用代理最值得養成的習慣。** 讓它直接修，你會得到一個看起來能動、但你不理解的變更。分兩步，你才有機會否決錯誤的方向。

## 範例三：建構／修改（可改指定範圍）

### 任務背景

範例二診斷完成，你選定了方案，現在授權 Codex 動手。

### GCSV Prompt（請複製後修改）

```markdown
## Goal
修正結帳頁的運費計算：配送方式為「門市自取」時，運費必須為 0 且不顯示運費列。

## Context
- 根本原因已確認：`src/checkout/calcShipping.ts:52` 未處理 `PICKUP` 這個 enum 值。
- 採用方案 A（在計算函式入口提前返回 0），不採用方案 B。

## Scope
- 可修改：`src/checkout/calcShipping.ts` 與其對應測試檔。
- **不可修改**：任何 API 的輸入／輸出型別；不要調整其他配送方式的既有行為。
- 遵循 repo 現有的程式風格，不要引入新套件。

## Verification
- 新增一個回歸測試，涵蓋 `PICKUP` 情境。
- 執行 `npm test`，必須全部通過。
- 完成後提供 diff 摘要，並說明你**沒有**動到哪些相關檔案。
```

> **課堂重點**：`Scope` 裡的「不可修改」比「可修改」更重要。沒寫的部分，代理容易「順手優化」。

## 範例四：產出文件與資料

### 任務背景

主管要一份可簽核的月度營運報告。你有原始 CSV，要產出 `.xlsx` 或 `.docx`。

### GCSV Prompt（請複製後修改）

```markdown
## Goal
依 `data/2026-08_配送績效.csv` 產出一份月度營運報告試算表（.xlsx），供部門會議使用。

## Context
- 讀者：物流部主管與各區站長
- CSV 欄位：日期、區域、單量、準時率、平均配送時數、異常件數
- 報告用途：找出準時率低於 95% 的區域並說明可能原因

## Scope
- **不要修改原始 CSV。** 產出檔請放在 `reports/` 目錄。
- 數字必須與來源一致，不可自行推估或補值。
- 若某欄位有空值，在報表中標註「資料缺漏」，不要用 0 代替。

## Verification
- 產出 `reports/2026-08_配送績效報告.xlsx`，包含：
  - 「明細」工作表：完整原始資料，首列凍結
  - 「摘要」工作表：各區彙總 + 準時率排序
  - 「異常」工作表：僅列出準時率 < 95% 的區域
- 在對話中附上你計算摘要數字所用的邏輯，讓我可以核對。
```

> **與 Claude 的差異**：Claude 需要你上傳 CSV 到對話。Codex **直接讀 workspace 裡的檔案**，產出檔也直接寫進 workspace，不需要下載再上傳。相對地，你必須明確指定「不要改原始檔」。

## 範例五：長時工作（`/goal`）

### 任務背景

要把 `tideflow-portal` 從舊的日期函式庫遷移到新的，牽涉數十個檔案。這種工作需要多步驟、需要你中途介入調整方向。

### 操作方式

在 ChatGPT 桌面版、Codex CLI 或 IDE extension 中輸入 **`/goal`** 進入長時工作模式。goal 的文字同時是**初始提示**與**完成條件**——Codex 會用它來驗證自己的進度。

```markdown
## Goal
將整個 repo 的日期處理從 moment.js 遷移到 date-fns，且行為完全不變。
完成條件：repo 內不再出現 `from "moment"`，且 `npm test` 全綠。

## Context
- 目前有 40+ 個檔案 import moment。
- 專案已有完整測試，覆蓋率約 80%。
- 時區處理集中在 `src/lib/datetime.ts`，這個檔案最需要小心。

## Scope
- 分批進行：先做 `src/lib/`，通過測試後再做 `src/api/`，最後做 `src/ui/`。
- **每一批完成後暫停，等我確認再繼續。**
- 不可修改測試的斷言內容——測試是我們判斷行為未變的依據。
- 不要順手做其他重構。

## Verification
- 每批結束時回報：改了哪些檔案、測試結果、你不確定的轉換點。
- 最終：`grep -r "from \"moment\"" src/` 無結果，且 `npm test` 全綠。
```

> [!IMPORTANT]
> **`/goal` 與 Automations 的差別**：`/goal` 是**一次性的多步驟工作**，需要人在旁邊掌舵，執行中可以暫停、恢復、編輯、清除。週期性重複的工作請用 [Automations](../Automations/README.md)。

## ❌ 反例對照：同一個需求的差別

| ❌ 常見寫法 | ✅ 改寫後 |
| :--- | :--- |
| 「幫我看一下這個專案」 | 「整理專案用途、技術棧與目錄結構；不要改檔；列出你無法確認的項目」 |
| 「結帳頁有 bug，修一下」 | 「重現步驟如下…；先只診斷不修復；指出檔案與行號並附證據」 |
| 「順便把測試也修好」 | （拆成獨立 task） |
| 「做得漂亮一點」 | 「遵循 repo 現有風格；不要引入新套件」 |
| 「應該可以了吧？」 | 「執行 `npm test` 並貼出實際輸出」 |

## 小結

| GCSV 欄位 | 沒寫會怎樣 |
|------|----------|
| **Goal** | 它做了事，但不是你要的事 |
| **Context** | 它花很久摸索，或猜錯檔案 |
| **Scope** | 它「順手」改了你沒預期的地方 |
| **Verification** | 它說完成了，你沒辦法反駁也沒辦法確認 |

**下一步**：把 `Scope` 裡每次都要重複的規則搬到 [`AGENTS.md`](../Agent_Configuration/README.md)，你的 task 會短一半。
