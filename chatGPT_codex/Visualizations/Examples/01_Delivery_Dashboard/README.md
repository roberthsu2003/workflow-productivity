# 視覺化範例 01：配送績效互動儀表板

> 🔵 **方案需求**：Visualizations 需 Plus 起。**Codex CLI 與 IDE extension 不支援 visualization 呈現**——請用桌面版或網頁版。

**情境**：主管要在月檢討會上看配送績效，但他不想看 48 列的 CSV。他想要「點一下就能切換區域」的東西。

---

## 📂 示範資料

[`delivery_performance_2026.csv`](./sample_files/delivery_performance_2026.csv) — 4 區 ×12 月，48 列。

**資料中有三個埋伏**（與 [Drive 分析章節](../../../Connectors/01_Google_Workspace/01_Drive_Analysis/README.md)共用同一套）：

| 狀況 | 位置 | 視覺化時的挑戰 |
| :--- | :--- | :--- |
| **真異常** | 東區 2026-08，準時率 81.3% | 會在圖上形成明顯低谷——要標註原因 |
| **離群但正常** | 南區 2026-11，單量 2.3 倍 | 會壓縮 Y 軸讓其他月份看不清 |
| **資料缺漏** | 中區 2026-06，整列空白 | **不可畫成 0**，會變成假的斷崖 |

---

## 🥇 練習一：先決定怎麼處理缺漏值

> [!WARNING]
> **這是視覺化最容易騙人的地方。**
>
> 中區 6 月沒有資料。如果畫成 0，圖上會出現一個急降到底再彈回來的 V 型——看起來像重大營運事故，實際上只是系統移轉沒落帳。

```markdown
@Visualize

在畫圖之前，先回答我：`delivery_performance_2026.csv` 中
中區 2026-06 的資料缺漏，在折線圖上有哪幾種畫法？
各自會讓讀者產生什麼印象？

不要畫圖，只做分析。
```

### 三種畫法的比較

| 畫法 | 讀者的印象 | 是否誤導 |
| :--- | :--- | :---: |
| 畫成 0 | 「六月中區崩了」 | ❌ **嚴重誤導** |
| 用前後月內插 | 「六月中區正常」 | ❌ 誤導（假裝有資料） |
| **線段斷開 + 標註「資料缺漏」** | 「六月沒資料」 | ✅ **正確** |
| 整條線不畫 | 「中區沒資料」 | ⚠️ 過度（其他 11 個月是有的） |

**正確答案是第三種。**

## 🥈 練習二：建立儀表板

```markdown
@Visualize

讀取 sample_files/delivery_performance_2026.csv，
建立 2026 年配送績效的互動視覺化。

## 需求
- 可切換「全部區域 / 單一區域」
- 主圖：準時率折線（含 95% 目標線；東區另有 92% 目標線）
- 副圖：配送單量長條
- 滑鼠移上去顯示：單量、準時率、平均時數、異常件、客訴件、備註

## 資料處理（重要）
- **中區 2026-06 資料缺漏 → 折線在該點斷開，並標註「資料缺漏」。
  不可畫成 0，不可內插。**
- **南區 2026-11 單量為平時 2.3 倍（雙 11 檔期）→ 保留真實數值，
  但在圖上標註原因，避免讀者誤判為資料錯誤。**
- 東區 2026-08 的低谷 → 標註備註欄的颱風原因。

## 限制
- 不要更動原始 CSV。
- 數字必須與來源完全一致。

## 驗收
下方附三點洞察，每點須指出是從哪個數字看出來的。
```

## 🥉 練習三：處理離群值造成的 Y 軸壓縮

南區 11 月的 33,489 件，會讓其他月份的 6,000～18,000 全部擠在圖表下方。

```markdown
@Visualize

承上圖。南區 11 月的離群值壓縮了 Y 軸，其他月份的差異看不出來。
請提出三種解法並各做一版，讓我比較。

每一版都要說明：
- 這個做法讓什麼變清楚了
- 這個做法**犧牲了什麼**
- 什麼情況下不該用這個做法
```

### 三種常見解法

| 解法 | 好處 | 代價 |
| :--- | :--- | :--- |
| **對數座標軸** | 所有月份都看得清 | 一般讀者容易誤讀比例 |
| **斷軸（break axis）** | 保留線性直覺 | 視覺上仍會低估落差幅度 |
| **分成兩張圖**（常態月／檔期月） | 兩者都清楚 | 失去了「一眼看完整年」 |

> [!IMPORTANT]
> **沒有標準答案。** 這題的價值在於讓學員意識到：**每一種圖表選擇都在強調某些東西、隱藏某些東西。**
>
> 「照著資料畫」不是中立的——選擇座標軸範圍本身就是一種詮釋。

## 🏁 練習四：無障礙檢查

```markdown
@Visualize

檢查目前這個視覺化的無障礙品質：
1. 色彩對比是否足夠（WCAG 2.1 AA）
2. 是否**只用顏色**區分區域？色盲使用者能分辨嗎？
3. 能否用鍵盤操作？
4. 是否尊重「減少動態效果」的系統偏好？

找出問題後修正，並說明你改了什麼。
```

> **第 2 點最常出問題。** 四條顏色不同的折線，紅綠色盲的讀者可能看到兩條一樣的線。
> 解法：**顏色 + 線型（實線／虛線／點線）雙重編碼**。

## 🆚 Visualization vs. Sites：什麼時候該升級

| | Visualization | Sites |
| :--- | :---: | :---: |
| 互動 | ✓ | ✓ |
| 可分享網址 | ✗ | **✓** |
| 資料持久 | ✗ | **✓** |
| 快速建立 | **✓** | ✗ |

**這個練習用 Visualization 就夠了**——你是在會議上投影，不需要網址。

如果需求變成「讓四區站長每天自己上去看」，才該升級成 [Sites](../02_Brand_Sales_Site/README.md)。
