# 02｜多步驟拆解：循序規劃與分階段交付

在單回合對話中，若你直接要求 AI「產出一份 3000 字的年度行銷計畫」，AI 通常會跳過深度思考，直接吐出看起來很長、實則泛泛而談的內容。

要產出高品質的成果，關鍵在於**「多步驟拆解（Multi-step Pipeline）」**：強制 AI 先思考、再規劃、再產出，並且**分階段交付中間產物**。

---

## 核心觀念：Pipeline（管線化）思維

在程式開發中，我們常把一個複雜處理拆解成 Pipeline：
**前一個函式的輸出（Output），就是下一個函式的輸入（Input）。**

```mermaid
flowchart LR
    S1[步驟 1：萃取核心資訊與限制] -->|分析結果| S2[步驟 2：擬定結構大綱]
    S2 -->|確認大綱| S3[步驟 3：撰寫主體細節]
    S3 -->|初稿內容| S4[步驟 4：格式整合與檢核]
```

### 為什麼要有「中間產物」？
如果只讓 AI 輸出最終成果，我們無法得知它中間做了哪些假設、忽略了哪些限制。  
規定 AI 在每個步驟輸出**「可看見的中間產出（Intermediate Artifacts）」**，使用者才能在第一時間審核：
- 步驟 1 的分析有沒有偏離需求？
- 步驟 2 的規劃方向是否正確？
- 若步驟 1 就錯了，後面根本不需要繼續做！

---

## 通用工作流程模板（ROSES - Steps 核心）

```markdown
# 角色與目標
你是一位［專業角色］。請協助我完成［最終可交付成果］。

## 背景資訊與限制
［提供原始資料、背景與邊界條件］

## 執行步驟（請依序嚴格執行，勿跳步）
1. **分析階段**：仔細檢視提供的資料，列出核心要點、潛在限制與缺漏資訊。
2. **規劃階段**：依據分析結果，提出 2-3 個處理方向或結構大綱，並說明各方向的優缺點。
3. **產出階段**：依據最優方向，撰寫具體、詳實的成果內容。
4. **檢核階段**：核對成果是否完全符合背景資訊中所提及的限制。

## 輸出格式要求
請依序分段輸出：
- 【階段 1：關鍵資訊分析】
- 【階段 2：結構大綱規劃】
- 【階段 3：完整成果內容】
- 【階段 4：符合性檢核紀錄】
```

## 由淺入深實戰範例

### 範例 1（基礎・教學）：規劃 50 分鐘程式課堂活動

當教師需要備課時，直接要教案往往不切實際，必須先確認先備知識與時間分配：

```markdown
# 角色與目標
你是一位資深資訊教育講師。請為國中生設計一堂 50 分鐘的 Python 課堂活動教案。

## 教學主題與學生程度
- 教學主題：Python 的串列（list）基本操作（建立、取值、append）。
- 學生程度：剛學過變數命名、資料型態（int, str）與基礎 if 判斷，第一次接觸容器概念。

## 執行步驟
1. **先備知識評估**：列出學生本堂課必須用到的既有觀念，並標註學生最容易混淆的點（例如：索引從 0 開始）。
2. **時間分配規劃**：將 50 分鐘依序劃分為「暖身喚醒（5m）」、「概念講解與範例（15m）」、「動手實作（20m）」與「成果分享收尾（10m）」。
3. **實作任務設計**：為 20 分鐘的動手實作設計一個具趣味性、生活化的小任務，包含題目說明與範例提示。
4. **時間核對**：計算各環節時間加總，確認精確等於 50 分鐘。

## 輸出格式
請輸出 Markdown 表格：
| 階段名稱 | 分配時間 | 教師活動 | 學生活動 | 階段檢核成果 |
|---|---|---|---|---|
（表格後請附上實作任務的完整題目說明與測試資料）
```

### 範例 2（進階・產品設計）：新功能規格提案（PRD 草案）

軟體產品經理在交辦工程團隊前，需要清晰的使用者故事與驗收標準：

```markdown
# 角色與目標
你是一位資深軟體產品經理（Senior PM）。請為我們的團隊協作 SaaS 工具撰寫「待辦事項 @提及提醒」的功能規格草案（PRD）。

## 背景與痛點
- 現狀：使用者在卡片留言指派工作時，被指派人往往無法即時得知，造成訊息延遲。
- 目標：引入 `@username` 自動通知與集中式通知中心未讀提示。

## 執行步驟
1. **問題定義與使用者故事**：撰寫 3 組具體的 User Story（身為［使用者角色］，我希望［做什麼事］，以便於［獲得什麼價值］）。
2. **使用者旅程拆解**：列出從使用者鍵入 `@` 到被提及者收到通知並點擊跳轉的完整操作路徑。
3. **驗收條件清單（Acceptance Criteria）**：使用 Given-When-Then 格式，列出正常流程與 2 個邊界情況（例如：提及不存在的使用者、被連續提及多次）。
4. **非功能性需求盤點**：列出對於即時性、通知延遲容忍度與權限安全性的考量。

## 輸出格式
請依序輸出：
1. 【User Stories】
2. 【User Journey Steps】
3. 【Acceptance Criteria (Given-When-Then)】
4. 【Non-functional Requirements】
```

### 範例 3（專家・商業行銷）：B2B 客戶提案簡報架構拆解

針對高價值企業客戶的提案，必須從商業痛點層層推進到客製化解決方案：

```markdown
# 角色與目標
你是一位專攻 B2B 企業軟體解決方案的資深 Pre-sales 顧問。請為製造業客戶規劃一份 15 頁的「產線 AI 瑕疵檢測系統」提案簡報架構。

## 客戶背景
- 客戶類型：中大型汽車零件代工廠。
- 核心痛點：人工目檢疲勞導致漏檢率達 3%，客戶客訴罰款沉重，且品檢老師傅面臨退休斷層。
- 預算與決策者：工廠營運副總（注重 ROI 與導入期產線不停機）。

## 執行步驟
1. **痛點與商業衝擊萃取**：將客戶痛點轉換為金錢與產能損失的量化評估面向。
2. **簡報敘事架構規劃**：採用「現狀挑戰 ➔ 商業損失 ➔ 解決方案 ➔ 成功案例 ➔ 投資回報 ROI」五段式黃金架構。
3. **頁次明細展開**：規劃全份 15 頁簡報，定義每一頁的標題、核心訊息（Key Takeaway）與建議視覺圖表呈現方式。
4. **防禦性檢驗**：檢查簡報架構是否正面回應了決策者「不停機導入」與「投資回收期」的最大疑慮。

## 輸出格式
請輸出：
- 客戶商業痛點量化摘要表
- 15 頁簡報逐頁規劃清單（頁碼、頁面主題、核心主張、推薦視覺呈現）
- 決策者關鍵疑慮回應對照表
```

## 邁向 Skill 的先修意義

在未來的 **AI Agent Skill** 中：
- 一個複雜任務通常會被寫成一個 **Workflow / State Machine**。
- 每個步驟都有明確的 **Pre-condition（前置條件）** 與 **Post-condition（後置產出）**。
- 學會使用自然語言精確拆解多步驟，未來撰寫自動化 Agent 的工作規格時，就能信手拈來，邏輯分明！
