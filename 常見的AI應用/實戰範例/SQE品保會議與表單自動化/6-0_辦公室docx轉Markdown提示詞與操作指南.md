# 步驟 0：辦公室 docx 轉 Markdown 提示詞與操作指南（專案工作流前置關鍵）

> 💡 **教學核心觀念**：  
> 在真實的企業辦公室中，**幾乎 100% 的原始文件都是 `.docx`**（例如錄音轉文字逐字稿、訪廠稽核筆記、長官交辦備忘錄）。  
> 然而，直接把二進位的 docx 丟給 AI 進行深度結構化分析，容易浪費大量 Token 且受到底層 XML 標籤雜訊干擾。  
> 
> 因此，在「專案工作流（Project Workspace）」中，我們建立的第一道標準作業程序（SOP）就是：  
> **保留辦公室原生的 docx 檔案，並教學生手動透過 AI 將其轉化為純淨結構化的 `.md` 檔案，再展開後續的人機協作！**

---

## 🛠️ 教學情境：如何在專案中將 docx 轉為 Markdown？

在 Google Antigravity、Claude Projects、ChatGPT 專案工作區或 Cursor IDE 中，你只需將辦公室原始檔 [`20260813_MRB會議逐字稿_原始檔.docx`](./20260813_MRB會議逐字稿_原始檔.docx) 放入專案資料夾，並向 AI 輸入以下提示詞：

## 📋 複製以下轉換提示詞交給 AI 執行

```markdown
你是一位具備資深軟體工程思維的辦公室自動化助理。

在我們的專案資料夾中，有一份辦公室原生的會議錄音逐字稿 Word 檔案：
檔案路徑：`20260813_MRB會議逐字稿_原始檔.docx`

請讀取該檔案中的所有文字內容，並將其完整轉換為純文字 Markdown 格式，要求如下：
1. 【語意完整保留】：嚴格保留逐字稿中的所有對話細節、爭論過程、零件料號、數量與人名，絕對不可擅自刪減或過度摘要內容。
2. 【段落分明與人類友善閱讀排版】（關鍵核心）：
   - 原 docx 錄音文字為 8,600 多字無換行之連續口語流水帳（文字牆），極不適合人類閱讀與工程師審核，必須重新排版為「段落分明、版面舒適、易於速讀」的格式。
   - **劃分結構化主題章節**：依會議進程加入 Markdown 二級標題區隔討論主題，例如：
     - `## 主題一：藍機右殼外觀、配套庫存與報廢判定爭議`
     - `## 主題二：黏結下齒板 24.1 長度修整、新絳熱處理與財務簽核要求`
     - `## 主題三：黏結凸輪 19 度測試、成型燒結變形與公差調整評估`
   - **依發言輪替與語意轉折切段**：根據「說話者更換」、「提問與回答」或「邏輯轉折」進行自然分段，每個段落建議長度約 2~5 句話，段與段之間以空行分隔，徹底杜絕巨型文字區塊。
   - **修整標點符號與語意斷句**：修補語音辨識之缺失標點符號（補上適當的逗號、句號、冒號、問號與引號），使句意明確流暢。
   - **數據與料號高精準呈現**：保留所有關鍵零件料號、公差數字（如 24.1、19度、±0.5度、±1度、5條、10條）與人名（如老朱、David、成樺、竹翔）。
3. 【消除格式雜訊】：去除所有二進位標籤、Word 底層 XML 樣式、字型屬性與無用空白，輸出純淨的 Markdown 格式。
4. 【輸出與存檔】：請在開頭加上會議日期（2026年08月13日）與主題（藍機右殼外觀、黏結下齒板24.1長度修整、黏結凸輪19度測試），並將結果儲存至專案檔案：
   `MRB會議逐字稿素材.md`

完成後，請向我回報檔案已建立完成，並列出轉換後的字數、劃分的段落數與三大核心討論主題摘要。
```

## 🌟 為什麼要教學生「保留 docx，轉為 Markdown」？四大關鍵優點

| 比較維度 | 直接餵原始 `.docx` 給 AI | 先手動轉為 `.md` 再人機協作（推薦） |
| :--- | :--- | :--- |
| **可讀性與人工審核** | ❌ 錄音檔多為無換行連續文字牆，人類肉眼難以閱讀檢驗 | ✅ **段落分明、章節清楚，人類工程師 30 秒快速定位關鍵決策** |
| **Token 消耗** | ❌ 額外耗費大量 Token 解析壓縮檔與 XML 標籤 | ✅ **純文字傳輸，Token 節省 50% ~ 70%** |
| **語意理解準確度** | ⚠️ 容易受到隱藏樣式標籤干擾，數字或料號偶有失真 | ✅ **語意純淨，料號、公差數字 100% 清楚明瞭** |
| **專案管理與版控** | ❌ 二進位檔無法進行文字差異比對（Diff） | ✅ **Git 或文字編輯器一秒比對修改歷程，清晰透明** |
| **辦公室實務接軌** | 脫離辦公室真實情境 | ✅ **完美兼顧「辦公室 docx 生態」與「AI 最佳文字中介」** |
