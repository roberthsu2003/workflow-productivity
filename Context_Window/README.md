# 🪟 Context Window（上下文視窗）核心觀念

> 💡 **核心認知**：  
> **當前所有 AI 服務與商業模式，本質上全部都是「以使用的 Token 數為計價方式」！**  
> 不論是 API 的實體美元扣款，還是網頁版（如 ChatGPT Plus / Claude Pro）的「每幾小時限制幾則訊息」，背後耗盡額度的元兇都是 **Token 消耗量**。  
> 
> AI 並沒有真正永久的記憶，在同一個對話 Session 裡能接續話題，是因為每次發送訊息時，系統都會把**「前面的歷史對話全部打包重新傳送」**！理解 Context Window 疊加與 Token 計費本質，是提升產能、省下真金白銀的必修課。

---

## 💰 1. 現代 AI 的商業本質：以 Token 為計價基礎（Pay-per-Token）

不管是個人訂閱還是企業整合，你必須明白：**AI 不是按「時間（分/秒）」計費，也不是按「按了幾次回車」計費，而是 100% 按照「處理與生成的 Token 數量」來算錢！**

* 🔤 **什麼是 Token？**  
  可以把 Token 想成是 AI 世界的「字詞積木」。英文大約 1 個單字 ≈ 1.3 個 Token；中文一個繁體字通常佔 **1 ~ 2 個 Token**。
* 🧾 **計價的真實樣貌**：  
  當你看到官方定價寫著 `$3.00 / 1M input tokens` 與 `$15.00 / 1M output tokens`，意味著你送進去讀的字、和 AI 吐出來的字，每一毫秒都在跳表計費。
* ⚠️ **網頁版用戶為什麼也會受影響？**  
  即使你付了月費（如每月 $20 美元），官方為了伺服器成本，仍會設定總 Token 流量上限。**如果對話累積太長，每一輪消耗的 Token 暴增，你很快就會撞到「請在 3 小時後再試」的冷卻限制！**

---

## 🔄 2. 對話是「一直疊加」的：Session 的背後真相


很多初學者以為：「我和 AI 來回聊了 10 輪，第 10 輪只花一句話的費用。」  
**事實正好相反！** 在同一個對話視窗（Session）內，內容是**持續滾雪球累加**的：

```
【第 1 輪】
用戶：問題 A (100 tokens)
AI  ：回答 A (200 tokens)
👉 消耗：100 (Input) + 200 (Output) = 300 tokens

【第 2 輪】
用戶：問題 B (100 tokens)
👉 背後實際送給 AI 的是：【問題 A + 回答 A】 + 問題 B
👉 消耗：(100 + 200 + 100) (Input) + 回答 B (200 Output) = 600 tokens！

【第 N 輪】
👉 每次送出，都在為歷史所有對話付費！
```

> 📌 **黃金法則**：  
> **「減少不必要的多輪對話，或在換主題時主動開啟新對話（New Chat），能大幅減少重複消耗的 Token 數量與費用！」**

## 🪙 3. 認識三種 Token 類型

在現代大語言模型（如 Claude 3.5 / GPT-4o）的計費與運作中，Token 主要分成三大類：

| Token 類型 | 中文稱呼 | 角色與運作機制 | 成本/速度特點 |
| :--- | :--- | :--- | :--- |
| **Input Tokens** | **輸入 Token** | 使用者送出的提示詞、上傳的附件，以及**前文累積的所有歷史對話**。 | 每次呼叫時計算，累積越多讀取越慢。 |
| **Output Tokens** | **輸出 Token** | AI 當下一個字一個字「推理生成」出來的新文字內容。 | **成本通常是 Input 的 3~5 倍**，生成越多越貴、耗時越長。 |
| **Cached Tokens**<br>*(Prompt Caching)* | **快取 Token** | 現代模型（如 Claude / GPT）的快取技術。若前文（如長合約、System Prompt、專案知識庫）未變動，系統直接命中暫存記憶。 | **成本大幅降價（通常打 1~2 折）**，且回應速度顯著提升！ |

## 🎯 4. 注意力機制（Attention）的極限：太長會失去焦點

現代模型的 Context Window 雖然已經高達 128K 甚至 200K Tokens（相當於數十萬字），但**「裝得下」不代表「看得清」**：

### ⚠️ 「迷失在中間」（Lost in the Middle）現象
模型底層採用 **Transformer 注意力機制（Attention Mechanism）**。當輸入的 Context 過長、包含太多輪無關對話或冗長雜訊時：
1. **注意力分散**：AI 容易過度聚焦在「剛開頭」與「最新幾句」，而忽略了夾在中間的重要規則。
2. **指令衝突**：前幾輪說的舊指令，可能與後面的新需求矛盾，導致 AI 認知混亂。
3. **幻覺機率上升**：雜訊越多，模型的推理邏輯越容易被帶偏。

```
┌─────────────────────────────────────────────────────────────┐
│ 🧠 AI 的注意力分配分布                                       │
│                                                             │
│  [ 開頭設定 (System Prompt) ] ➔  高注意力 ⭐⭐⭐⭐          │
│  [ 漫長的第 2 ~ 15 輪雜音對話 ] ➔  注意力嚴重稀釋 💤 (易漏看) │
│  [ 最新輸入 (Current Prompt) ] ➔  高注意力 ⭐⭐⭐⭐          │
└─────────────────────────────────────────────────────────────┘
```

## 📄 5. 極致省 Token 秘訣：中間過程一律「純文字化」


在職場實務中，使用者最常餵給 AI 的是實體辦公檔案：`.docx`、`.xlsx`、`.pptx`、`.pdf`。  
但很多人不知道：**直接上傳這類二進位/複雜封裝檔，會吃掉驚人的 Token，並嚴重浪費 Context Window！**

### 💡 核心痛點：為什麼原始檔案超吃 Token？
- **PDF / Word (`.docx`)**：包含大量 XML 標籤、字型樣式、邊界留白與版面元數據（Metadata）。AI 在背後解析時，往往需要先把整份檔案轉成巨大的底層資料結構，消耗大量 Input Tokens。
- **Excel (`.xlsx`)**：包含儲存格公式、色彩格式、巨集設定與跨工作表關聯，原始解析相當臃腫。
- **PowerPoint (`.pptx`)**：夾帶大量的投影片母片座標、動畫標籤與視覺框線代碼。

---

### 📊 Excel 要轉成什麼純文字格式最好？

針對試算表（Excel），在純文字處理時主要有兩種選擇：

| 純文字格式 | 特點與優勢 | 最佳適用場景 |
| :--- | :--- | :--- |
| **CSV**<br>`(Comma-Separated Values)` | **⭐⭐⭐ Token 消耗最精簡、最省額度！**<br>只有逗號分隔純數據，完全沒有多餘的裝飾符號。AI 呼叫 Python（Pandas）處理時最原生、最不易出錯。 | **資料筆數多（超過 50 行）**、需要進行數據加總、數學運算或統計分析。 |
| **Markdown 表格**<br>`(\| 欄位 \| 欄位 \|)` | **直觀易讀，結構語意清晰。**<br>人類看得舒服，AI 也很擅長文字比對，但多了 `\|` 與 `-` 符號，Token 會比 CSV 稍微多一些。 | **資料筆數少（30 行以內）**、欄位包含較多文字說明、需要人類與 AI 同時快速肉眼檢閱。 |

> 📌 **總結選型**：  
> - **單純要 AI 算數學、洗資料** ➔ **轉成 `.csv`（最省 Token、算得最準）**  
> - **需要 AI 閱讀審閱、對照文字說明** ➔ **轉成 `Markdown` 表格**

---

### 🔄 辦公檔案的「純文字三階段工作流」

為了在多輪對話中將 Token 消耗降到最低，務必建立 **「中間純文字、最後才出成品」** 的思維：

```
【第一步：前置輸入】
Word / PDF / PPTX / Excel
       ⬇️ （轉為純文字）
【第二步：中間反覆討論與推理】⭐ 全程使用純文字（最省 Token）
📄 Markdown（文章、簡報大綱、會議紀錄）
📊 CSV / Markdown Table（試算表數據）
       ⬇️ （定稿確認）
【第三步：最終成果封裝】
🎯 透過 AI 呼叫工具 / Python 生成最終要交差的 .xlsx / .pptx / .docx / .pdf
```

### 🚀 為什麼這個流程能節省高達 70% 的 Token？（實戰效益分析）

| 階段與機制 | ❌ 傳統低效做法（每輪傳實體檔） | ✅ 純文字三階段做法（Markdown / CSV） | 💡 實戰效益分析 |
| :--- | :--- | :--- | :--- |
| **1. 草稿討論階段**<br>*(第 1 ~ 5 輪來回修潤)* | 每次修改都上傳新的 Word/Excel，或要求 AI 每次都吐出實體二進位檔案。 | 中間討論只傳遞純文字（Markdown 條列點或大綱），完全不碰實體檔。 | **大幅減輕 Input Token**：每次歷史疊加的只有幾百字的乾淨純文字，沒有龐大的 XML/二進位封裝雜訊。 |
| **2. 運算與排版處理**<br>*(數據清洗與核對)* | 直接請 AI 解析 50 頁複雜格式試算表，容易算錯且單次 Token 暴衝。 | 先轉成純數據的 `.csv` 或輕量表格再交給 AI 分析運算。 | **運算精準度 100% 且極省**：CSV 只有純數字與逗號，計算不易出錯且完全不浪費空間。 |
| **3. 最終成果交付**<br>*(定稿後最後一哩路)* | 每一輪都在等 AI 重新打包檔案，提早耗盡每 3 小時的對話流量上限。 | 內容、數字與大綱 100% 確認後，**最後一句指令才叫 AI 調用 Python 匯出實體檔**。 | **終極省 Token**：整場對話只在最後一步產生一次實體檔案輸出，省下超過 **70%** 的 Token 額度與等待時間！ |

### 💬 實戰 Prompt 範例模板（隨插即用）

學員在日常工作中，可以直接套用以下「三階段提示詞範例」：

#### 📊 場景 A：處理 Excel 報表數據（Excel ➔ CSV 討論 ➔ 正式 Excel）

* **🔹 步驟一：上傳檔案並要求轉純文字討論（節省 Token 關鍵！）**
  > **Prompt**：  
  > 「這是我上傳的本季業績 raw data（.xlsx）。**請先幫我把這份資料的核心欄位轉換成純文字的 CSV 格式輸出在畫面上，先不要生成任何實體檔案**。接下來我要針對這份 CSV 數據和你討論毛利率異常與分店排名。」

* **🔹 步驟二：中間反覆分析與調整（全程用純文字對話）**
  > **Prompt**：  
  > 「請根據剛才的 CSV 數據，找出銷售額低於 50 萬的分店，並幫我計算出平均客單價，以 Markdown 表格列出分析結果。」

* **🔹 步驟三：確認定稿，最後一步才輸出實體檔案**
  > **Prompt**：  
  > 「剛才討論與計算出的分析數據已經定稿。**現在請你寫一段 Python 程式碼，將剛才確認好的數據與分析摘要，正式匯出為一份排版工整的 Excel（.xlsx）檔案供我下載**。」

---

#### 📑 場景 B：長篇報告轉簡報（Word/PDF ➔ Markdown 討論 ➔ 正式 PPTX）

* **🔹 步驟一：長文萃取成結構化 Markdown 大綱**
  > **Prompt**：  
  > 「這是一份 30 頁的年度計畫書（.pdf）。**請先不要生成任何投影片檔案，只要幫我提煉出 10 頁 PPT 的『Markdown 結構大綱』即可**（每頁包含：標題、3 點核心重點、演講者備忘稿）。我們要先就文字大綱進行修改。」

* **🔹 步驟二：微調大綱內容（只修改純文字，極省額度）**
  > **Prompt**：  
  > 「第 4 頁的市場分析重點太過抽象，請幫我修改該頁的 Markdown 條列點，強化競品對比與具體市佔率百分比。」

* **🔹 步驟三：文字定稿，輸出正式 PPT 簡報**
  > **Prompt**：  
  > 「整份 10 頁的 Markdown 簡報大綱已經確認無誤。**請使用 Python 或 PPTX 工具，將這份大綱套用專業科技風格配色，正式生成一份 .pptx 簡報檔案給我**。」

## 🛠️ 最佳實務操作原則（Best Practices）

1. **中間過程一律純文字，最後一步才輸出實體檔**：
   - 討論架構與數據時用 Markdown / CSV；定稿後再讓 AI 生成 Word / Excel / PPTX。
2. **一事一對話（Task-oriented Session）**：
   - 一個任務告一段落，準備進行全新主題時，**請開新對話（New Chat）**，避免為歷史無關內容持續付費。
3. **長文精簡後再餵**：
   - 餵給 AI 的資料盡量先做初步篩選，剔除無關廢話或無效排版，保留核心文字。
4. **善用快取（Prompt Caching / Projects）**：
   - 在 Claude Projects 或固定 System Prompt 中放置不變的參考資料，享受 Cached Tokens 的高速與 1~2 折低成本優勢。
5. **發現 AI 開始鬼打牆時，立刻「斷捨離」**：
   - 當 AI 累積過多錯誤脈絡時，與其在原本的對話裡不斷糾正，不如把修正後的指令**複製到全新的對話視窗重新開始**！
